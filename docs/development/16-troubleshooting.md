# Troubleshooting

Owner: Engineering. Reviewed: 2026-10-16.

Use this guide to diagnose the Phase 0–1 checkout without weakening its gates or network protections. Run commands from the repository root unless stated otherwise. Do not print or paste `.env`, publish internal ports, or point tests/migrations at data you need to preserve.

## 1. Tool versions and dependency installation

### Bun or Node is the wrong version

1. Check `node --version` and `bun --version` in a fresh terminal. Use Node `24.x` and Bun `1.4.3` (`bun.lock` and CI are authoritative). The default Node runtime is in `>=24 <25`; Dockerfiles pin `24.22.0`.
2. Install the supported versions from the upstream Node/Bun installation sources in [developer onboarding](11-developer-onboarding.md#2-prerequisites), then open a new terminal so `PATH` points at the new installation.
3. Run `bun install --frozen-lockfile` from the repository root again. Do not edit or delete the lockfile to address a runtime-version mismatch.

### `bun install --frozen-lockfile` fails

1. Check that the command runs from the repository root and Bun reports exactly `1.4.3`.
2. Confirm network access to the configured npm package registry and check the first package/error in the output. The same frozen install is used by CI.
3. Do not substitute `npm install`, remove `bun.lock`, or commit a lockfile generated by a different package manager. If registry access is the only blocker, record the install as not run and use the CI result once available.

### A dependency policy check fails

- `check:licenses` reports the detected package and licence expression. Follow `docs/development/02-dependency-policy.md`; do not add a licence exception without the owner decision and policy update.
- `check:advisories` needs live npm registry access. It fails closed when `registry.npmjs.org` is unreachable; an unavailable registry is not a clean advisory result. Re-run when connectivity is restored.
- A moderate/low advisory is printed for review; high/critical findings fail the check. Do not suppress the finding or lower its severity threshold.

## 2. Environment file and startup validation

### Backend says a variable is missing, invalid, or still a placeholder

1. Run `bun run env:create` from the repository root if `.env` does not exist. It generates local values and refuses to overwrite an existing file.
2. Run `git check-ignore .env` to confirm the local file is ignored. Never copy `.env.example` directly: its angle-bracket values are deliberate placeholders.
3. If you intentionally customize a setting, use the exact variable spelling and format in [the configuration reference](14-environment-and-configuration.md). Backend error messages name variables and problems without printing their values.
4. Check the start command's configuration source. Backend processes load `.env` with process-environment overrides. The static web server reads process environment only; Compose supplies its settings. Vite reads its `VITE_*` variables when started/built.
5. Do not paste `.env` into an issue, terminal transcript, chat, or PR. Report only the variable name and a redacted error.

**Important:** `bun run env:create --force` overwrites `.env` and generates new passwords. If the existing database roles were created with the old values, those new credentials will not match the database until roles are deliberately reinitialized. Do not regenerate credentials as a first-line debugging step. Reset procedures that delete data are marked in [onboarding](11-developer-onboarding.md#9-reset-the-local-environment--destructive-operations).

### `.env` exists but the web/API still uses unexpected values

- Host-run dev scripts merge `.env` values with process settings and set per-service values for their child processes. Existing shell environment values override file values for backend config; `scripts/dev.mjs` also assigns its computed backend values.
- A changed `VITE_*` variable is build-time configuration. Restart Vite or rebuild the web workspace to pick it up; editing `.env` does not change an already-loaded browser bundle.
- Compose interpolates values when it creates/recreates services. Inspect the effective non-secret configuration with `docker compose config`; never use `docker compose config --environment` or paste the resolved output if it contains credentials.

## 3. Database and migration failures

### Compose `db` does not become healthy

1. Check `docker compose ps --all db` and `docker compose logs --tail 80 db` from the repository root.
2. Confirm Docker Engine/Compose is running and `.env` contains the generated `POSTGRES_PASSWORD`. Compose fails closed when it is absent.
3. Confirm the host port is available and `DB_PORT` is a valid number. PostgreSQL is published only as `127.0.0.1:${DB_PORT:-5432}:5432`; an occupied port can prevent the container from starting.
4. Do not change the mapping to `0.0.0.0` or publish `5432` as a troubleshooting shortcut. The protected bind is intentional.
5. If you believe the local named volume is incompatible or corrupted, stop and preserve it before considering a reset. `docker compose down --volumes` is **destructive**: it deletes the local `db-data` PostgreSQL cluster.

### `bun run db:migrate` cannot connect or refuses to initialize

1. Confirm the selected database path is running: `docker compose ps db` for Compose, or the `bun run dev:db` ready log for embedded PostgreSQL.
2. For host-run CLI commands, confirm `DB_ADMIN_URL` and the three role passwords exist in `.env`; do not print them. For Compose, the `migrate` service builds its admin URL from `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` and requires all three service-role passwords.
3. Run `bun run db:status` to inspect migration state. The CLI prints a redacted connection target and does not reveal passwords.
4. Read the first error from the migration runner. A checksum mismatch means an applied migration file was changed; do not edit applied migrations to silence it. Follow the [failed-migration rollback runbook](../operations/runbooks/failed-migration-rollback.md) and request review.
5. `bun run db:rollback` reverses one migration for each service and changes the database. It can remove schema objects/data created by that migration. **Do not use it on a database with valuable data without a separately reviewed backup and recovery plan.**

### `/healthz` works but `/readyz` fails

- `/healthz` proves the process is running; it does not query PostgreSQL. `/readyz` performs the database readiness check and returns HTTP 503 when the database cannot be reached.
- Check that the selected host/port, database name, and service role match the database path in use. The Core API uses the `boro_core` role, Relation uses `boro_relation`, and SOS uses `boro_sos`.
- In Compose, services connect to `db:5432` using Compose DNS, not the host's `DB_PORT`. In host-run mode, scripts use `localhost:${DB_PORT:-5432}`.
- Run `bun run db:status` after the database is reachable. Do not treat an HTTP 200 from liveness as proof that migrations or business features are available.

### Dockerless embedded database does not start

1. Check that `bun run build` has completed successfully and no process is already bound to `DB_PORT` (default `5432`).
2. Start `bun run dev:db` from a non-elevated PowerShell 7 session on Windows. PostgreSQL refuses to run its postmaster as an administrator.
3. Read the first startup error in that terminal. Keep the process running while host-run services/tests need the database; Ctrl+C stops it but retains the persistent cluster.
4. Do not delete `var/pg-dev/` to work around a startup error. Removing this directory is **destructive** and permanently erases that embedded development cluster. Preserve or back it up before any deliberate reset.

### PostgreSQL integration tests fail to start or clean up

1. Confirm the Node version is 24 and workspace dependencies/build output are available; run `bun run build` before the targeted integration suite if needed.
2. By default, the harness starts a disposable embedded PostgreSQL 18 server. Inspect the first `packages/test-utils` setup error and confirm the platform can execute the installed PostgreSQL binary.
3. If `TEST_DATABASE_URL` is set, the harness uses that external server and creates/drops isolated databases there. Unset it for the default embedded path, or use only a disposable PostgreSQL instance. **Never set it to production or to a database whose contents must survive.**
4. Tests create and drop databases and are configured not to run files in parallel. A failed run may leave temporary files under the operating system's temporary directory; it does not require deleting the Compose `db-data` volume.

## 4. Ports, browser proxy, and container network

### A port is already in use

1. Read the service's startup error and identify the actual port. Host-run defaults are API `3000`, Relation `3001`, SOS `3002`, metrics `9000`–`9002`, and Vite `5173`.
2. Stop only the local process that owns the conflicting port, or choose an available supported host-run port through its documented setting. For the database, set `DB_PORT` and align `DB_ADMIN_URL`/`DATABASE_URL` with the new host port (`env:create` seeds them for `5432`); for Vite, set `VITE_PORT`. If you change the browser's Vite or Compose `WEB_PORT`, align `WEB_ORIGIN` and `CORS_ALLOWED_ORIGINS` with that origin. Recheck the proxy target when changing the Core API port.
3. Compose internal service ports `3000`–`3002` and metrics ports `9000`–`9002` are private and are not host-published. Do not add `ports:` entries to them for convenience.
4. Compose's PostgreSQL and web host mappings bind to loopback by default. Keep `127.0.0.1`; widening the web mapping exposes its `/api/*` proxy too. See [PR #6](https://github.com/komeilm76/boro_biya/pull/6) and the [port reference](14-environment-and-configuration.md#6-port-and-exposure-reference).

### The web shell loads but `/api/*` returns an error

- With Vite, verify the Core API is running on the target selected by `API_PROXY_TARGET` (normally `http://127.0.0.1:3000`). Vite forwards `/api` requests; the browser should use relative paths rather than a backend hostname.
- With the Compose web edge, verify `api` is healthy and the web container's fixed `API_ORIGIN` is `http://api:3000` on the Compose network. Check `docker compose logs --tail 80 api web`.
- A 404 error envelope for an unknown `/api/v1/*` path is expected in Phase 1: there are no business routes yet. A request path that resolves does not imply that an authentication, map, or SOS API exists.
- Vite rejects Host headers that are not in its allowlist. If a trusted local preview requires a hostname, configure that exact value in `VITE_ALLOWED_HOSTS`; do not use an allow-all setting or expose the preview as a production service.

### CORS or browser origin validation fails

- `WEB_ORIGIN` for the Core API must be an absolute `http://` or `https://` URL matching the web origin. The host Vite default is `http://localhost:5173`; Compose defaults to `http://localhost:8080`.
- `CORS_ALLOWED_ORIGINS` is a comma-separated list of explicit bare origins. The schema rejects wildcards, non-HTTP(S) schemes, paths, usernames, query strings, and fragments in every environment. Configure only credential-free origins; the current schema does not separately check a password-only user-information field.
- The default relative `/api` proxy avoids cross-origin browser requests. Do not set `VITE_API_BASE` to an absolute backend URL; Phase 1 validation accepts only empty or root-relative paths.

## 5. Build, typecheck, and test failures

### TypeScript/Vue build fails

1. Run `bun run typecheck` and `bun run build` from the repository root; capture the first failing workspace and file.
2. Check that the changed workspace imports its declared dependencies and that browser-safe code does not import `config`, `db`, or `server-runtime`. Run `bun run check:deps` after changing workspace manifests or imports.
3. Build order is calculated from workspace manifests. Do not work around a cycle by hand-editing build output under `dist/`; build artefacts are generated and ignored.
4. `apps/android` is a Capacitor configuration-only workspace. The orchestrator skips native Android packaging until Phase 8; an Android build is not a Phase 1 verification requirement.

### Formatting or lint changes many files

- `bun run format` is check-only; `bun run format:fix` and `bun run lint:fix` modify files. Inspect `git diff` immediately after either fix command and revert only unintended formatting changes.
- Markdown is ignored by Prettier. Run `node scripts/gates/phase0.mjs` to verify Markdown structure and links rather than reformatting the normative docs.
- Do not use a formatter or lint suppression to remove a substantive rule failure.

### Documentation gate says a page is missing, stale, or date-invalid

1. Ensure every normative doc has an H1, an exact `Owner: <role>. Reviewed: YYYY-MM-DD.` header, and an index row in `docs/README.md`.
2. Confirm links are repository-relative and their targets exist. The gate checks both documents and index metadata.
3. Check whether the checkout is shallow:

   ```text
   git rev-parse --is-shallow-repository
   ```

4. If it prints `true`, fetch complete history from the base before interpreting a review-date/history skip. In a shallow checkout only, the documented Git operation is:

   ```text
   git fetch --unshallow origin main
   ```

5. Re-run `node scripts/gates/traceability.mjs` and `node scripts/gates/phase0.mjs`. Do not change roadmap statuses or review dates merely to silence a failure; dates must reflect an actual review.

## 6. Docker or production operations are unavailable

- If Docker Engine/Compose is not installed, the Compose stack, image builds, live port-binding assertions, and full-stack smoke checks cannot be run locally. Record these as **not run because Docker is unavailable**; source-only checks do not prove a container build or runtime behaviour.
- The Compose stack is for development and CI, not a documented production deployment. There is no repository-verified production rollout, backup/restore, availability objective, monitoring operations team, or public build/install process. Do not adapt the Compose file into an internet-facing deployment.
- The static web edge is plain HTTP and explicitly lacks TLS/HSTS, connection/rate/body limits, and production proxy hardening. A real deployment requires an independently reviewed TLS-terminating reverse proxy with the operational controls documented in `docs/operations/README.md`; the actual hosting decision remains open.
- Do not put credentials in logs while diagnosing production prerequisites. Follow the [security reporting process](../../.github/SECURITY.md); acknowledge within 7 working days and make an initial triage/accept-or-reject decision within 21 working days. The 21-day target is not a remediation deadline.
