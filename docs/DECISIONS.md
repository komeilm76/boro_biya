# Architecture Decision Log and Open Questions

Decisions are recorded here, never inferred from code. An open question is never silently converted into a permanent assumption.

Owner: Repo owner. Reviewed: 2026-10-16.

## Status vocabulary

| Status | Meaning |
| --- | --- |
| `Proposed` | Written down and ready for owner review; not yet binding. |
| `Accepted` | Binding. Changes require a superseding ADR. |
| `Accepted (mandatory)` | Binding security/product constraint from the security baseline; weakening it requires explicit owner risk acceptance with an expiry. |
| `Accepted (owner decision, YYYY-MM-DD)` | Binding; the repository owner made the call personally on that date. Used where the decision needed the owner rather than an engineering default. |
| `Deferred` | Deliberately not decided yet, with a named phase and owner. |
| `Superseded by ADR-xxx` | Kept for history; the newer ADR governs. |

## ADR template

```text
### ADR-0NN — <short title>
**Status:** Proposed | Accepted | Accepted (mandatory) | Accepted (owner decision, YYYY-MM-DD) | Deferred | Superseded by ADR-0NN
**Date:** YYYY-MM-DD  **Owner:** <role>
**Context:** <the forces, constraints, and evidence that make a decision necessary>
**Decision:** <what is decided, in one or two sentences, using MUST/SHOULD per README>
**Alternatives considered:** <each with the reason it was not chosen>
**Consequences:** <costs accepted, what becomes easier/harder, follow-up work>
**Revisit when:** <measurable trigger, or "not planned">
```

## Decisions

### ADR-001 — Core architecture
**Status:** Accepted  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** Two capabilities (relations, SOS) are required to be independently deployable, while the rest of the product is a single coherent application. Splitting every domain into a microservice would multiply operational, memory, and networking overhead for a small team.  
**Decision:** The core API is a modular monolith; Relation and SOS are independently deployable services with their own APIs, schemas, and release cycle.  
**Alternatives considered:** Full microservices (rejected: operational cost unjustified for current scale); single monolith including relations and SOS (rejected: contradicts the standalone-service requirement and prevents independent deployment).  
**Consequences:** Module boundaries inside the core must be explicit and testable so future extraction stays cheap; cross-service communication needs contracts and idempotency.  
**Revisit when:** Measured scaling, isolation, or team-boundary needs justify further decomposition.

### ADR-002 — Plugin ZIP security
**Status:** Accepted (mandatory)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** An admin-uploadable package is an untrusted archive. Executing it in the core process or with host privileges converts an upload form into remote code execution and host compromise.  
**Decision:** Uploaded plugin code is never executed in the core process or with host privileges. Packages pass quarantine, structural validation, signature/provenance checks, dependency/licence review, isolated build, staged container deployment with least privilege and resource/network limits, health verification, and admin activation, with rollback and audit. ZIP-driven installation stays disabled in production until the Phase 7 gate passes.  
**Alternatives considered:** In-process plugin loading (rejected: no isolation boundary); manual out-of-band deployment without a package workflow (rejected: loses auditability and the product requirement).  
**Consequences:** Plugin installation requires container-runtime capabilities and an operator-managed trust store; plugin development has a build step rather than a drop-in file.  
**Revisit when:** A different isolation technology (for example WASI sandboxes) is proven safer and cheaper than containers, with an accepted ADR.

### ADR-003 — Location sharing
**Status:** Accepted (mandatory)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** Location is sensitive personal data, and a "share with followers" feature is the highest-risk data flow in the product.  
**Decision:** Live sharing is off by default, and no relationship implies access. **Live publication requires an explicit, time-boxed grant that names the individual follower receiving it** ([ADR-013](#adr-013--live-location-sharing-is-a-time-boxed-session)); there is no follower-wide live stream. Last-known coordinates follow the accepted relationship plus the owner's last-known preference, are labelled with timestamp and accuracy, expire per retention policy, and are never presented as live. A **history trail is supported only through explicit per-follower history sharing** ([ADR-014](#adr-014--location-history-sharing-is-opt-in-and-retention-bounded)). Publishing stops promptly on grant expiry or revoke, session end, opt-out, unfollow, or block.  
**Alternatives considered:** Opt-out model with sharing on by default (rejected: violates consent-based sharing); sharing with all authenticated users (rejected: no privacy model); an indefinite toggle with a follower-wide audience (rejected: the owner cannot limit how long they are exposed, and a follower accepted once would keep receiving positions — see ADR-013).  
**Consequences:** Location ranking/notification features must tolerate the common case where most users share nothing; the UI must state absence of sharing rather than implying presence, and must show, per follower, how much time remains on that follower's grant.  
**Revisit when:** Not planned. Retention specifics are refined by [Q-06](#open-questions) and [Q-22](#open-questions); the grant model itself is refined by [ADR-013](#adr-013--live-location-sharing-is-a-time-boxed-session).

### ADR-004 — Realtime transport
**Status:** Proposed — binding only after owner acceptance; Phase 4 must not start with it open (it is named in the Phase 4 exit criteria).  
**Date:** 2026-10-13  **Owner:** Engineering  
**Context:** Most realtime needs are one-way feeds (SOS status, notification updates, admin dashboards). WebSocket infrastructure costs more to operate, secure, and load-test.  
**Decision:** Use SSE for one-way server-to-client feeds, and add Socket.IO/WebSocket only where bidirectional low-latency behaviour is required and justified in a new ADR. Authenticate and authorize every subscription and re-check on permission change.  
**Alternatives considered:** WebSocket everywhere (rejected: extra operational cost without a proven need); long-polling (rejected: worse latency and connection churn at the target scale).  
**Consequences:** Browser authentication for SSE uses a cookie session or a short-lived stream ticket because `EventSource` cannot send headers; connection limits and heartbeats must be implemented and load-tested.  
**Revisit when:** A feature demonstrably requires client-to-server messaging on the same connection.

### ADR-005 — Geospatial database
**Status:** Deferred (decision required before Phase 4)  
**Date:** 2026-10-13  **Owner:** Engineering  
**Context:** Nearby-user search for SOS dispatch and viewport queries for alerts/POIs need indexed spatial queries. PostGIS adds an extension dependency to the database image, backups, and deployment target.  
**Decision:** Not yet decided. Before Phase 4, prototype the nearest-user query on representative data, benchmark PostGIS against an indexed bounding-box + exact-distance approach, verify extension availability in the Docker image and the production deployment target (including backup/restore), and record the result as an accepted ADR.  
**Alternatives considered:** PostGIS (richest query support, extra operational dependency); plain `(latitude, longitude)` indexes with bounded candidate sets (no extension, requires careful query design); a separate geospatial store (rejected: additional system for a small dataset).  
**Consequences:** Until decided, no code may perform unbounded distance scans, and the dispatch query must be written behind a repository interface so the implementation can change without touching domain logic.  
**Revisit when:** The Phase 4 prototype provides numbers.

### ADR-006 — API contract source of truth and OpenAPI dialect
**Status:** Accepted (owner decision, 2026-10-13)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** The pack requires OpenAPI 3.1 as the public contract and the project tools (`km-api`, `zopia`) where verified. Verification on 2026-10-13 showed: `km-api@0.4.1` is an endpoint/schema builder documented as **OpenAPI 3.0** compatible with a peer dependency on `zod ^4.3.6`; `zopia@0.7.1` converts between Swagger 2.0 / OpenAPI 3.0.x / 3.1.x, JSON Schema, and Zod v4, depends on `km-api ^0.4.1` and `zod ^4.0.0`, and its reverse conversion defaults to OpenAPI 3.1. Neither tool is a Fastify plugin; both are schema/contract tooling.  
**Decision:** TypeScript endpoint definitions plus Zod v4 schemas are the single source of truth. The published contract is generated to **OpenAPI 3.1** by `zopia`, and CI validates it with the OpenAPI validator plus `zopia validate`/`zopia diff`. If a required construct cannot be represented in 3.1 without loss (nullable vs optional, discriminators, recursive schemas, `additionalProperties`, binary uploads), the loss is recorded as a fixture and regression test; the generator is fixed or the construct is expressed differently — never silently degraded. If 3.1 fidelity cannot be achieved for a construct the API needs, the fallback is an OpenAPI 3.0.3 document plus an explicit note in the API reference, and that fallback requires owner acknowledgement.  
**Alternatives considered:** Hand-written OpenAPI document as source of truth (rejected: drifts from validation code); OpenAPI 3.0 as the default output (rejected: 3.1 aligns with JSON Schema 2020-12, which is what Zod emits); dropping the project tools (rejected: they are requested and verified to exist and work with Zod v4).  
**Consequences:** Zod v4 is the only supported Zod major (both tools require it). Contract tests must exist per construct; a tool upgrade requires re-running the fidelity fixtures.  
**Revisit when:** Either tool changes its supported inputs, or a required construct fails the fidelity fixtures twice.

### ADR-007 — Runtime and toolchain baseline
**Status:** Accepted (owner decision, 2026-10-13)  
**Date:** 2026-10-13  **Owner:** Repo owner + Engineering  
**Context:** The pack prefers Bun "where compatibility is verified" and requires exact, verified versions. Verification on 2026-10-13: Node 24 is Active LTS (maintenance from 2026-10-20), Node 26 becomes Active LTS on 2026-10-28; Vitest 5 requires `^22.12 || ^24 || >=26`; Vite 8 requires `^20.19 || >=22.12`; VueUse 15 requires `>=22`; ESLint 10 requires `^20.19 || ^22.13 || >=24`; `typescript-eslint@8` accepts `typescript >=4.8.4 <6.1.0`, so npm's `typescript@latest` (7.0.2) is **outside** the supported peer range. Bun 1.4.x provides built-in Argon2id (`Bun.password`), removing a native dependency from the security-critical password path.  
**Decision:** Node.js 24 LTS is the baseline runtime for repository tooling and CI, the guaranteed compatibility target for every workspace, and — since [Q-16](#open-questions) was answered — **the production runtime** ([ADR-025](#adr-025--nodejs-24-lts-is-the-production-runtime-bun-is-the-development-toolchain)). Bun 1.4.x is the preferred package manager and script runner, where compatible with the pinned dependency set. All application code must run correctly on Node 24 and must not depend on Bun-only runtime APIs, except behind an explicitly swapped adapter (password hashing, for example). TypeScript is pinned to the 6.0.x line, not 7.x, until `typescript-eslint` supports it.  
**Alternatives considered:** Node-only toolchain (simpler, loses Bun's speed and built-in Argon2id); TypeScript 7 (rejected for now: unsupported peer range); Bun-only (rejected until the compatibility spike proves the full toolchain).  
**Consequences:** CI runs a Node 24 matrix (and adds Node 26 after its LTS promotion), the runtime baseline is documented in the dependency policy, and the Phase 1 spike verifies Vitest/Vite/Fastify behaviour under Bun **as a toolchain** — the server-runtime question it was originally written to settle is closed by ADR-025.  
**Revisit when:** Node 26 is LTS and the matrix is green; the toolchain half is revisited if Bun stops being compatible with the pinned set.

### ADR-008 — Single-replica core API until shared state exists
**Status:** Accepted  
**Date:** 2026-10-13  **Owner:** Engineering  
**Context:** Rate limiting, lockout counters, session revocation, idempotency records, and SSE subscriptions must be correct across the deployment. In-memory implementations silently break when more than one replica serves requests. The pack also requires measuring before adding infrastructure such as Redis.  
**Decision:** The core API and each service run as a **single replica** in v1. This is a correctness constraint, not a preference. Scaling beyond one replica requires an accepted ADR that names the shared store, defines failover behaviour, and covers the failure mode where the store is unavailable (fail-closed for security-relevant counters).  
**Alternatives considered:** Multi-replica with sticky sessions (rejected: does not protect lockout counters and revocation); introducing Redis immediately (rejected: unmeasured additional dependency).  
**Consequences:** Availability during a single-replica restart depends on fast startup and graceful shutdown; deployment documentation must state the constraint; load tests must include reconnect storms against one instance.  
**Revisit when:** Multiple replicas are needed for availability or capacity, or a measured requirement justifies a shared store.

### ADR-009 — UI framework strategy for web and Android
**Status:** Accepted (owner decision, 2026-10-13)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** The pack lists Vuetify, Tailwind, Ionic Vue, and Capacitor together and asks to "share the Vue application where practical". Vuetify (Material components with its own SASS utilities), Tailwind (utility CSS with preflight resets), and Ionic (mobile components with their own theming and router expectations) overlap in styling, layout, and navigation. Combining all three in one application produces specificity conflicts, duplicated theming, larger bundles, and ambiguous ownership of component behaviour.  
**Decision:** The web/PWA application is built with **Vuetify + Tailwind** (Vuetify for components, Tailwind for layout utilities, with preflight scoped so it cannot reset Vuetify's base). Ionic Vue is used **only** in the Android shell and only for native-shell affordances (safe areas, navigation transitions, hardware-back handling, native plugin integration) plus Capacitor APIs; shared product screens stay framework-neutral Vue components and are rendered by both hosts. If the Phase 8 spike shows that the split costs more than it saves, the fallback is a Capacitor-only Android build without Ionic, or an Ionic-only mobile UI sharing only stores/contracts with the web app — the choice must be recorded as a superseding ADR with bundle-size and maintenance evidence.  
**Alternatives considered:** All three everywhere (rejected: conflicting concerns); Ionic for web too (rejected: web needs desktop-grade components); Vuetify-only with Capacitor (viable fallback, kept as the cheaper alternative).  
**Consequences:** Component libraries must not leak into `packages/contracts`/`packages/validation`; shared screens must avoid library-specific APIs; a bundle-size budget per platform is required.  
**Revisit when:** The Android shell spike (Phase 8) or a bundle-size regression provides evidence.

### ADR-010 — Phase 0 / Phase 1 gate boundary
**Status:** Accepted  
**Date:** 2026-10-13  **Owner:** Engineering  
**Context:** The Phase 0 exit condition previously required "CI gates run on a minimal skeleton" while Phase 1 was defined as the phase that creates the skeletons and the CI. That made Phase 0 impossible to complete without starting Phase 1.  
**Decision:** Phase 0 delivers documentation and the **documentation gates** (inventory, requirement-ID coverage, link, placeholder, and secret-pattern checks) runnable locally and in CI, with no application code. Phase 1 delivers the workspace skeleton, pinned dependencies with a lockfile, application CI (format, lint, typecheck, unit, integration), Docker Compose startup, and health/readiness endpoints. The Phase 0 exit gate is satisfied by the documentation gate passing plus owner review.  
**Alternatives considered:** Keeping the original wording (rejected: self-contradictory); creating a throwaway skeleton in Phase 0 (rejected: violates "no feature implementation").  
**Consequences:** The CI workflow in Phase 0 runs only documentation gates; the full gate catalogue is introduced incrementally with the phase that can satisfy it (see [CI and gates](development/03-ci-and-gates.md)).  
**Revisit when:** Not planned.

### ADR-011 — Documentation architecture and requirement identifiers
**Status:** Accepted  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** The documentation pack lived at the repository root while the master prompt declared `/docs` the source of truth; there were no requirement identifiers, so phase exit criteria ("acceptance criteria with pass/fail evidence") and the pull-request checklist had nothing stable to reference. The referenced `zopia` project solves the same problem with a two-audience split and numbered identifiers.  
**Decision:** All normative documentation lives under `/docs`, split by audience: `/docs/user/` (product users; never mentions phases, ADRs, or requirement IDs) and `/docs/development/`, `/docs/security/`, `/docs/performance/` (engineers and agents). Every binding requirement carries a permanent `AREA-NN` identifier, assigned when the requirement is written and validated mechanically by the documentation gate; the coverage of every identifier is tracked in [traceability](development/07-traceability.md) and enforced by the gate. Documentation and behaviour change in the same commit.  
**Alternatives considered:** Keep documents at the root (rejected: contradicts the master prompt and mixes audiences); identifiers only per document section (rejected: cannot be referenced from tests and pull requests).  
**Consequences:** Identifier assignment is a gate step, not a manual convention; adding, removing, or reordering requirements requires regenerating the traceability file, which the gate enforces.  
**Revisit when:** Not planned.

### ADR-012 — Relation and SOS are first-party services, not third-party plugins
**Status:** Accepted  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** The pack describes Relation and SOS as "the first two plugins" while also describing a third-party package lifecycle (upload, quarantine, signing, staged containers). Treating the two core product services as untrusted third-party packages would add the full Phase 7 machinery to Phase 4 and 5 and would leave the product without its central features until then.  
**Decision:** Relation and SOS are first-party services shipped from this repository, deployed from reviewed source with the same API contracts, health checks, versioning, and permission boundaries the plugin contract defines. They are not uploaded as ZIP packages and are not gated behind the Phase 7 security workflow. Third-party package installation (ZIP upload, signatures, isolation workflow) is delivered in Phase 7 and remains disabled in production until its gate passes.  
**Alternatives considered:** Ship Relation/SOS through the plugin pipeline (rejected: front-loads Phase 7 and blocks core features on plugin infrastructure); treat them as core modules (rejected: contradicts the standalone-deployable requirement).  
**Consequences:** The plugin capability model must be defined early enough for the two services to express permissions and capabilities, but the untrusted-package workflow can follow later; `PLUGIN_SYSTEM` §3 applies to third-party packages only.  
**Revisit when:** A genuinely third-party plugin is proposed.

### ADR-013 — Live location sharing is a time-boxed session
**Status:** Accepted (mandatory)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** An always-on live share exposes the owner for as long as they forget to switch it off. The owner asked to decide, each time they share, how long the share lasts.  
**Decision:** Live publication requires an explicit session with a mandatory `expires_at` chosen by the owner within a server-configured maximum ([Q-21](#open-questions) sets the default maximum), and the audience is chosen explicitly: **each share names the individual followers who receive it** (one grant per follower). There is no blanket "all followers" live stream. A session never renews or chains automatically; a single grant, or the whole session, can be ended at any moment, and sharing ends on expiry, opt-out, unfollow, block, or service unavailability, with the reason recorded ([DATA_MODEL](DATA_MODEL.md) `live_share_sessions`, `live_share_grants`).  
**Alternatives considered:** A single indefinite toggle (rejected: unbounded exposure); client-side countdown only (rejected: a client cannot be trusted to enforce privacy); a follow-wide live stream with a preference toggle (rejected by the owner: a follower who found you once should not silently keep tracking you); per-follower permanent grants (rejected: permanence defeats the time box).  
**Consequences:** Three things must not be confused — the sharing *preference* (may I share at all), the *session* (am I sharing right now), and the *grant* (who receives it); the API, UI, stream authorization, and tests must keep them distinct, the UI must show remaining time and an "end now" action **per follower**, and a follower must be selected from the accepted list rather than reached implicitly. Last-known location is deliberately different: it follows the relationship plus the preference, because it is a stale value its owner has already published.  
**Revisit when:** Phase 4, if the owner asks for scheduled or recurring shares, or for a limited "share with all current followers" convenience that still expires.

### ADR-014 — Location history sharing is opt-in and retention-bounded
**Status:** Accepted (mandatory)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** The owner asked that users be able to share location history with followers. This reverses the earlier "no history" stance, so history must now be designed as a first-class, bounded dataset rather than implicitly.  
**Decision:** A separate `user_location_history` table records points **only** while the owner has enabled history sharing; every row carries an expiry, the window is bounded by a server maximum and chosen by the owner ([Q-22](#open-questions) sets the default), and **only the individual followers the owner grants see the trail** (`history_share_grants`). Reads are paginated and never bulk-exportable, are re-authorized on every request against the grant, and the owner can delete the whole trail immediately. History is never derived from, or shown as, the live/current location.  
**Alternatives considered:** Treat history as an extension of `user_locations` (rejected: breaks the latest-point invariant and its TTL); retain history for all users and hide it by default (rejected: collecting what you do not need is the worst privacy posture); show the trail to every accepted follower while the toggle is on (rejected by the owner in favour of explicit per-follower grants); let followers control history visibility (rejected: not the owner's decision to delegate).  
**Consequences:** New schema, per-request authorization, and UI (toggle, window, delete, access list) ship with the Relation Service in Phase 4; deletion and expiry must be provable in tests; the retention job named in earlier drafts runs only when a deployment enables retention enforcement ([ADR-026](#adr-026--retention-and-deletion-are-policies-not-defaults-nothing-is-deleted-automatically-yet)), while expiry that makes a row unreadable and the owner's own delete do not depend on that switch; [Q-06](#open-questions) is now partly resolved (history *is* in scope) with only last-known retention left open.  
**Revisit when:** Phase 4; the retention numbers in [Q-22](#open-questions) must be agreed before any history code is written.

### ADR-015 — Assistance categories drive SOS dispatch
**Status:** Accepted (mandatory)  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** Location alone is a weak dispatch filter: the nearest person is often the wrong person. The owner asked for a user attribute (category) that every SOS alert also carries, so suggestions go only to users whose categories match the alert.  
**Decision:** A server-owned, admin-managed catalogue (`categories`) is added, and **each user holds exactly one category** (`user_categories`, unique per user). Every alert carries one or more active categories, recorded on the alert by reference to the catalogue (categories are deactivated rather than deleted, so the alert stays resolvable and auditable). Dispatch eligibility requires the user's category to be among the alert's categories, checked **before** distance ordering; a category assignment never grants authorization, and a category that requires verification only satisfies dispatch once an administrator has verified that user's category assignment. Catalogue and assignment changes are audited and only affect future dispatch.  
**Alternatives considered:** Free-text skills (rejected: unqueryable, spoofable, no admin governance); multiple categories per user (rejected by the owner in favour of exactly one, which keeps matching and accountability unambiguous); category as a plugin-provided taxonomy (rejected for v1: dispatch is core SOS behaviour, see [ADR-012](#adr-012--relation-and-sos-are-first-party-services-not-third-party-plugins)); category-as-role (rejected: roles are exactly `admin`/`user` — see [ADR-016](#adr-016--exactly-two-roles-an-assistance-category-is-not-a-role)).  
**Consequences:** Dispatch can now legitimately return nobody even with many users nearby; the UI and admin view must explain "no matching category" rather than silently showing an empty list, and the dispatch query in [ARCHITECTURE](ARCHITECTURE.md) must carry the match filter.  
**Revisit when:** Phase 5, if matching needs weighting, multi-category scoring, or per-category radii.

### ADR-016 — Exactly two roles; an assistance category is not a role
**Status:** Accepted  
**Date:** 2026-10-13  **Owner:** Repo owner  
**Context:** The owner restated that the system has two roles (`admin`, `user`) while also introducing categories, which could be mistaken for a permission system.  
**Decision:** Authorization recognizes exactly two roles: `admin` and `user` — the roles v1 seeds, now as data ([ADR-024](#adr-024--database-driven-roles-and-permissions-with-two-roles-seeded)). Assistance categories are profile/dispatch metadata: they never widen access to data, never gate an administrative capability, and MUST NOT be checked as an authorization boundary anywhere in the code. Their only effect is to include a user in a matching dispatch candidate set.  
**Alternatives considered:** Category-scoped admin (rejected for v1: reintroduces sub-roles through the back door and contradicts the owner's statement); implicit elevation for verified categories (rejected: verification proves subject knowledge, not trustworthiness in the product's security model).  
**Consequences:** [PRODUCT_REQUIREMENTS](PRODUCT_REQUIREMENTS.md) §1 keeps the roles v1 seeds to two, and the role set is now data rather than an enum — Q-17 was answered without abusing categories ([ADR-024](#adr-024--database-driven-roles-and-permissions-with-two-roles-seeded)); authorization tests assert that holding a category alone grants nothing.  
**Revisit when:** Phase 5, if the owner decides verified categories need a distinct operational view.


### ADR-017 — Internationalization: Persian and English ship together
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-15](#open-questions) asked which languages the first release requires, because the answer decides work that must exist before the first screen: text direction, the message catalogue, the calendar and numerals, the typeface, and the layout rules. The product is built for a Persian-speaking audience while the repository itself is documented in English ([GOV-41](development/00-repository-conventions.md)), and the two languages differ in direction, calendar, numbering, and typography. Retrofitting any of those once the authentication screens exist is precisely the cost the question was raised to avoid.  
**Decision:** The product ships **two complete locales in the first release**: Persian (`fa`, right-to-left) and English (`en`, left-to-right). No user-facing surface may ship in only one of them; every user-facing string comes from the message catalogue of the active locale ([GOV-63](development/00-repository-conventions.md), UI-21); a missing key fails the build ([QA-17](QUALITY_GATES.md)) instead of falling back silently to the other language; direction, calendar, numerals, and formatters follow the locale (UI-22, UI-25); and the language is chosen before sign-in, changeable at any time, and persisted in `user_preferences.locale` and `text_direction` ([DATA_MODEL](DATA_MODEL.md)), which already carry both fields. The initial language and the fallback order are settled separately ([Q-24](#open-questions)).  
**Alternatives considered:** Persian only for the first release (rejected by the owner: both languages are required); English first with Persian added later (rejected: RTL layout, catalogue plumbing, and typography are structural and must exist before the first screen); catalogue management through an external translation platform (rejected for v1: two locales, versioned with the code, no translator access management needed yet); a third locale in the first release (rejected for v1: nothing requires it and it multiplies review cost); machine translation at build time (rejected: unreviewed strings in an interface that carries an assistance feature).  
**Consequences:** Phase 2 delivers two complete catalogues, not one; `vue-i18n` joins the verified frontend baseline ([dependency policy](development/02-dependency-policy.md) §3); every string added later is added in both catalogues in the same change; the typeface must cover Persian glyphs, joining behaviour, and the zero-width non-joiner; text-rendering tests run per locale; a plugin that contributes interface text declares its locales and falls back to its own default ([PLUGIN_SYSTEM](PLUGIN_SYSTEM.md) §4, PLG-57); the repository's own documents stay English — this decision is about the product interface, not about translating the documentation set.  
**Revisit when:** a third language is requested, or a deployment deliberately ships a single language.

### ADR-018 — English is the default language; Persian is a complete translation

**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [ADR-017](#adr-017--internationalization-persian-and-english-ship-together) fixed which locales ship; it deliberately left open which one a visitor meets first, because that decides the language of the sign-in, registration, and recovery screens and the fallback chain when nothing matches. That question was [Q-24](#open-questions), and the owner has now answered it.  
**Decision:** English (`en`) is the **default language for every visitor on first use**. Device and browser language and `Accept-Language` do not select a language for now, so the first screen is the same for everyone and does not depend on a signal the pack cannot test. Persian (`fa`) ships as a **complete translation**, reachable before sign-in from the sign-in, registration, and recovery screens and at any time in settings (UI-12, UI-28). An explicit choice is stored and wins on later visits: against the account when signed in, on the device when signed out. Exactly these two locales ship in v1 — a third language is not added ([PRODUCT_REQUIREMENTS](PRODUCT_REQUIREMENTS.md) §10).  
**Alternatives considered:** Device or browser language with English as the fallback (rejected by the owner: the default must be English, and detection would make the first screen differ per visitor and per locale to test); Persian as the default (rejected: the default is English); server-side `Accept-Language` negotiation (rejected for the same reason, and it cannot see a saved preference before sign-in); more locales than these two (deferred: not needed for v1, and each additional catalogue multiplies the parity work `QA-17` enforces).  
**Consequences:** No locale detection is implemented, so there is no detection to test and no request header decides what a visitor reads; the pre-sign-in switcher (UI-28) is the only path into Persian before an account exists, which is why it stays a Phase 2 exit criterion; every user-facing surface — including the privacy notice (PRIV-31) — exists in both locales (ADR-017, UI-28); a saved choice is the only input that overrides the default, so it must survive sign-out and reinstall on the device and account switching for an account.  
**Revisit when:** a third language is requested, or the pre-sign-in switcher proves insufficient in use — in which case the fallback order (device language, then `Accept-Language`) becomes a new decision rather than an undocumented behaviour.

### ADR-019 — Username-only identity with no email address and no mobile number
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-01](#open-questions) asked whether an account's login identifier is the username alone, or whether verified email and phone are also supported. Recovery design, notification channels, the account schema, and the privacy duties all follow from the answer, and collecting a contact channel in a product that does not need one creates a data class with its own breach and retention obligations.  
**Decision:** The product collects and stores **neither an email address nor a mobile number**, and uses neither as a login identifier, a recovery channel, or a notification channel. An account is identified by its username alone ([AUTH-01](PRODUCT_REQUIREMENTS.md#3-authentication-and-account-recovery)). ### ADR-020 — Self-hosted privacy-first CAPTCHA
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner + Security  
**Context:** [AUTH-02](PRODUCT_REQUIREMENTS.md#login) requires a CAPTCHA challenge when the risk policy triggers it, and [SEC-11](SECURITY.md#2-identity-and-credentials) requires its provider to be consistent with the project's privacy commitments. [Q-02](#open-questions) asked which policy and which kind of provider, because a hosted CAPTCHA service receives user data, ships third-party code into the page, and brings retention terms the operator does not control.  
**Decision:** The challenge is **self-hosted and privacy-first**: adaptive challenges whose difficulty and trigger come from the configured risk policy; **server-side validation of the challenge token**; rate limiting on every endpoint that issues or validates one; minimal data collection (no browsing history, no device fingerprint, no advertising identifier); **no third-party requests or tracking**; documented retention and deletion rules for challenge records ([data classification](security/data-classification.md)); accessibility as a hard requirement (keyboard and screen-reader operable, never the only control, [UI-16](PRODUCT_REQUIREMENTS.md#9-accessibility-localization-and-resilience)); secure fallback behaviour — a challenge that cannot be validated denies the request ([SEC-03](SECURITY.md#1-security-baseline)), and the availability of any component never bypasses throttling or lockout; and automated tests for issuance, validation, replay, expiry, and accessibility. No third-party CAPTCHA service is used.  
**Alternatives considered:** A hosted CAPTCHA service (rejected: user data leaves the deployment, third-party scripts and tracking are unavoidable, and the retention terms are not ours to set); no challenge at all (rejected: AUTH-02 requires defence in depth, and throttling alone is what Q-02 asked to strengthen); an always-on challenge (rejected: AUTH-02 triggers the challenge from the risk policy, and a permanent challenge costs accessibility for every user).  
**Consequences:** The challenge implementation, its accessibility, and its test suite are ours to maintain, and its quality is a security dependency rather than a vendor's promise; challenge records are short-lived and never joined to profile or location data; the risk policy and the feature switch are configuration ([`.env.example`](../.env.example)); the dependency policy lists the implementation as a Phase 2 item with its licence and maintenance status checked; the threat model's spoofing row ([TH-01](security/threat-model.md#4-threats-and-mitigations)) keeps CAPTCHA as one control among several.  
**Revisit when:** The risk policy needs a signal that cannot be computed self-hosted, or the self-hosted challenge fails an accessibility review.

### ADR-021 — Bearer access tokens with rotating refresh tokens for web and Android
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-03](#open-questions) asked which session model the product uses: server-side cookie sessions, token plus refresh rotation, or both per client class. Session records, CSRF scope, native token storage, revocation, and the SSE authentication path ([OPS-25](ARCHITECTURE.md#3-realtime-model), [API-32](API_AND_OPENAPI.md#5-realtime-contracts)) all depend on it, and two clients — the browser SPA and the Android shell — must share one API.  
**Decision:** One model for both clients. Every protected request authenticates a **short-lived access token in the `Authorization: Bearer` header**; the client obtains it by presenting a **rotating refresh token**. Refresh tokens are single-use, recorded server-side as a hash and only as a hash ([DATA_MODEL](DATA_MODEL.md#core-identity)), rotated on every use, and bound to a token family so that presenting a consumed token is treated as reuse and revokes the family ([SEC-10](SECURITY.md#2-identity-and-credentials)). Web stores its refresh token in an `HttpOnly`, `Secure`, `SameSite` cookie (`__Host-` prefix where the deployment permits); Android stores it in Keystore-backed secure storage. Sessions are listed and revoked server-side ([PRIV-21](security/data-classification.md#5-privacy-defaults)); the authorization check runs in one server-side middleware on every protected operation ([SEC-25](SECURITY.md#4-authorization)). Only refresh, logout, and stream-ticket issuance are cookie-authenticated, and those carry CSRF protection ([SEC-09](SECURITY.md#2-identity-and-credentials)); browser `EventSource` streams authenticate with the single-use stream ticket, because they cannot send a header ([API-32](API_AND_OPENAPI.md#5-realtime-contracts)). No token is kept in `localStorage`.  
**Alternatives considered:** Server-side cookie sessions only (rejected: awkward for the Android shell and it makes every client carry cookie semantics, against the API-first rule); both models, one per client class (rejected: two session models to implement, test, and keep in agreement — the third option in the question); long-lived access tokens (rejected: a stateless token cannot be revoked before it expires, so its lifetime has to stay short); opaque server-side access tokens on every request (rejected: a datastore lookup per request for no security gain, since rotation and reuse detection already live on the refresh token).  
**Consequences:** Access tokens are stateless and therefore cannot be revoked before expiry — lifetimes stay short, sensitive operations re-authenticate ([SEC-26](SECURITY.md#4-authorization)), and a password change or account-state change revokes the refresh-token family so the next refresh fails; reuse detection is implemented and tested, not assumed; the `sessions` table stores hashed refresh-token material with a rotation generation and never a raw token; CSRF protection narrows to the cookie-authenticated operations; the client-side half of the model is documented for both platforms.  
**Revisit when:** Passkeys or device-bound credentials change the login flow, or a supported client cannot store a cookie or a platform-secure secret.

### ADR-022 — Abuse protection thresholds and the no automatic ban rule
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner + Security  
**Context:** [Q-04](#open-questions) asked for the lockout threshold, window, backoff, unlock path, and what may trigger an automated ban. [SEC-14](SECURITY.md#3-account-lockout-and-abuse-controls) and [SEC-19](SECURITY.md#3-account-lockout-and-abuse-controls) require numbers rather than adjectives, and [SEC-15](SECURITY.md#3-account-lockout-and-abuse-controls) forbids a lockout an attacker can make permanent.  
**Decision:** Per account, **10 failed attempts inside a rolling 15-minute window** ([LOGIN_MAX_ATTEMPTS_PER_ACCOUNT](../.env.example)) trigger a **15-minute lockout that expires on its own**, with progressive delays applied after repeated failures; per-origin counters apply independently so one account cannot be locked out from elsewhere and shared addresses are not treated as one attacker. Rate limits apply to every sensitive endpoint (login, registration, recovery, challenge issuance and validation, token refresh, privileged actions). The unlock paths are: automatic expiry, the owner's own password change, self-service recovery ([ADR-023](#adr-023--security-questions-stay-the-only-self-service-recovery-factor)), and administrator-assisted reset. **No automatic permanent ban** of a user or an address exists; an automated ban requires documented evidence of sustained malicious behaviour, is **disabled by default**, and always carries a review path ([SEC-17](SECURITY.md#3-account-lockout-and-abuse-controls)). Security events are logged without passwords, tokens, or other secrets ([SEC-13](SECURITY.md#2-identity-and-credentials)). Every threshold and window is configuration: development values are relaxed, production values are stricter and are reviewed before release.  
**Alternatives considered:** `Escalating lockouts` without a low cap (rejected: an attacker would gain a permanent denial-of-service against a victim, which SEC-15 forbids); permanent automatic IP bans (rejected by the owner: shared addresses punish bystanders and the evidence for the ban is thin); a fixed hard-coded policy (rejected: development needs relaxed values, production needs stricter ones, and SEC-19 requires configuration); removing lockout and relying only on delays (rejected: AUTH-04 and SEC-14 require a lockout state).  
**Consequences:** The `escalating lockout` reading is retired: the lockout is a fixed self-expiring duration and escalation applies to the bounded delay before it, which is how SEC-14 is now worded; the counters live in the shared store required by [ADR-008](#adr-008--single-replica-core-api-until-shared-state-exists) and are never the source of truth for account state ([DATA_MODEL](DATA_MODEL.md#core-identity)); ban stays an administrative act with actor, reason, timestamp, and audit ([SEC-16](SECURITY.md#3-account-lockout-and-abuse-controls)); the example values in [`.env.example`](../.env.example) are the development defaults, and choosing the production set is a Phase 9 review item.  
**Revisit when:** Measured abuse shows the thresholds are too weak or too strong, or the pre-release review sets the production values.

### ADR-023 — Security questions stay the only self-service recovery factor
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-05](#open-questions) asked which stronger recovery factors are permitted alongside security questions. [TH-02](security/threat-model.md#4-threats-and-mitigations) calls the questions the weakest path into an account, and the pack listed stronger factors as "planned", which a reader can mistake for approved work.  
**Decision:** Security questions are **the only self-service recovery factor** for now, and **no additional or stronger factor is implemented unless the owner explicitly approves it** — recovery codes, verified contact channels, and passkeys-as-recovery stay unapproved. Self-service recovery sits behind **one server-side feature switch** ([SECURITY_QUESTIONS_ENABLED](../.env.example)) that can be turned off globally, and per client class where the API supports it, without a code change; when it is off, the recovery endpoints reject attempts securely and generically, and **the user is warned before relying on the account** that a forgotten password can mean permanent account loss, with only administrator-assisted recovery remaining. Answers are normalized, salted, hashed with the same password-hashing algorithm as passwords ([SEC-06](SECURITY.md#2-identity-and-credentials)), rate-limited, never disclosed, and never logged.  
**Alternatives considered:** Adding a stronger factor now (rejected: not approved; the alternatives stay unapproved rather than half-built); removing security questions now (rejected: it would leave administrator-assisted reset as the only way back into an account); making recovery administrator-only (kept as the fallback path, not the primary one, because it does not scale and puts an admin in every recovery).  
**Consequences:** The recovery risk is accepted with a user-visible warning rather than mitigated away, and [threat model](security/threat-model.md) §6 records it that way; the switch, its per-client behaviour, and the warning are Phase 2 deliverables with tests; AUTH-13 … AUTH-20 stay as they are; and the pack's language of "planned" stronger recovery is replaced by "not approved" so no reader plans work the owner has not approved.  
**Revisit when:** The owner approves a stronger factor, or an incident shows the questions are being abused at scale.

### ADR-024 — Database-driven roles and permissions with two roles seeded
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [ADR-016](#adr-016--exactly-two-roles-an-assistance-category-is-not-a-role) fixed two roles for v1 and ruled that an assistance category is never a permission. [Q-17](#open-questions) asked whether a single `admin` role is sufficient or whether scoped operational roles are needed; the owner chose a model that can grow without a schema change, rather than a closed set that would make every future role a migration.  
**Decision:** Authorization is **database-driven RBAC**: permissions are defined centrally as data (resource + action), roles are rows carrying permissions, and users hold roles. **v1 seeds exactly two roles** — `admin`, which holds the full administrative permission set, and `user`, which is the default — and the existing endpoints keep working unchanged. **Authorized administrators can create, assign, modify, and revoke custom roles and their permissions without a code change or a migration**, which is why the model is data rather than an enum. Every check runs through one server-side authorization layer ([SEC-25](SECURITY.md#4-authorization)) instead of duplicated role comparisons, permissions are validated server-side on every change, the least-privilege principle applies, and permission granularity can reach a single resource or action. **The last active administrator cannot be removed**: any change that would leave no active account holding the full administrative permission set is rejected, audited, and covered by a test.  
**Alternatives considered:** Keeping the closed two-role enum (rejected by the owner: every new role would be a migration plus code changes); per-user role columns (rejected: it does not scale past two roles and duplicates the permission list); treating an assistance category as a permission (rejected: ADR-016 forbids it and the owner's answer repeats that permissions are defined centrally); leaving the last-administrator case unprotected (rejected: an administrator can otherwise lock the product out of its own administration, accidentally or deliberately).  
**Consequences:** ADR-016's two-role *set* stands for v1, but the role set is no longer a closed enum, so `users.role` becomes role-assignment data (`roles`, `permissions`, `role_permissions`, `user_roles` in [DATA_MODEL](DATA_MODEL.md#core-identity)), and ADM-01/ADM-02 are reworded to say so; tests assert that a custom role can be added as data, that every check goes through the one layer, and that removing the last administrator fails; the role-management screens and endpoints arrive with the first custom role, not in v1, and the API inventory says so; no document may treat `admin` and `user` as the only possible values.  
**Revisit when:** Custom roles are actually created (Phase 2 or later), or a role needs scoping finer than resource plus action.

### ADR-025 — Node.js 24 LTS is the production runtime; Bun is the development toolchain
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner + Engineering  
**Context:** [ADR-007](#adr-007--runtime-and-toolchain-baseline) fixed Node 24 LTS for repository tooling and CI and left one thing open: whether the API and services **run** on Bun in production ([Q-16](#open-questions)). Bun offers speed and a built-in Argon2id, and that is exactly the kind of gain that argues for taking a dependency the deployment cannot walk back from: a runtime-specific API in application code turns a later migration into a rewrite. The product ships a web client and an Android shell on their own build pipelines, so the backend runtime is not what those artefacts depend on.  
**Decision:** **Node.js 24 LTS is the production runtime for the API and every service.** **Bun is the preferred development toolchain and package manager** — installs, script running, and local workflows — used only where it is compatible with the pinned dependency set. The architecture stays **runtime-portable**: application code uses standard TypeScript, Web APIs, and Node-compatible libraries, and **Bun-only runtime APIs are prohibited in application code unless the owner explicitly approves one, and then only isolated behind an adapter with a Node implementation** ([GOV-82](development/02-dependency-policy.md#4-runtime-baseline), [GOV-90](development/02-dependency-policy.md#4-runtime-baseline)). The web client and the Android application are **built independently of the backend runtime** — their pipelines do not require the API to run and do not import backend-only modules — with pinned tool versions, a frozen lockfile, and CI that type-checks, tests, builds, and verifies production artefacts ([GOV-90](development/02-dependency-policy.md#4-runtime-baseline), [QA-11](QUALITY_GATES.md#1-required-gates), [QA-123](QUALITY_GATES.md#1-required-gates)). **Runtime compatibility and portability checks run in CI**, every production artefact records the runtime and exact versions it was built and tested with, and the deployment documentation states those versions and how to change the runtime ([OPS-84](ARCHITECTURE.md#7-configuration-and-environments)). The release gates of [QUALITY_GATES](QUALITY_GATES.md) §1 must pass on the exact commit before anything ships. Where a Bun-only shortcut would buy local speed at the cost of portability, **reliability, maintainability, and predictable web and Android releases win**.  
**Alternatives considered:** Bun as the production runtime (rejected by the owner: runtime-specific performance gains do not justify the portability cost, and the deployment would depend on a runtime with a younger production track record); Node as the development toolchain too, dropping Bun (rejected: Bun's install and script speed costs nothing while the code stays portable); running both runtimes in production per service (rejected: two runtimes to patch, two build recipes, and a split deployment story for no functional gain); using `Bun.password` in production for its built-in Argon2id (rejected with the runtime: on Node the maintained `argon2` binding provides the same algorithm, and the choice stays behind the password-hashing adapter).  
**Consequences:** The security-critical password path uses the maintained native `argon2` binding on Node ([SEC-05](SECURITY.md#2-identity-and-credentials)), with the adapter boundary that makes a future runtime swap a configuration change rather than a rewrite; `Bun.password` is not a production dependency, and [ADR-007](#adr-007--runtime-and-toolchain-baseline)'s note that it removes a native dependency no longer applies — the native-dependency obligation in [GOV-79](development/02-dependency-policy.md#1-principles) is accepted deliberately; CI adds a compatibility job that builds and starts each artefact on the pinned Node version and fails on portability violations; the dependency policy records Node as the runtime and Bun as the toolchain ([GOV-81](development/02-dependency-policy.md#4-runtime-baseline), [GOV-82](development/02-dependency-policy.md#4-runtime-baseline)); contributor documentation keeps `bun install` and `bun run …` as the local path (CI and repository tooling use Node 24, [01-development-environment](development/01-development-environment.md#2-prerequisites)); a runtime change later is a new decision against this one, not an edit.  
**Revisit when:** A measured operational need (performance, memory, or deployment constraints) shows Node 24 LTS cannot meet the documented budgets, and the portability rules above make the migration cost known in advance.

### ADR-026 — Retention and deletion are policies, not defaults: nothing is deleted automatically yet
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-14](#open-questions) asked what the retention, deletion, and export obligations are for user data and audit logs. The question could not be answered as a universal product rule, because the product is deployed per operator ([ADR-027](#adr-027--deployment-specific-law-and-data-residency-no-single-jurisdiction)) — and the pack had drifted into describing the answer it did not have: the retention table read as an enforcement schedule, and the account-deletion and data-export paragraphs read as implemented workflows. Deleting is irreversible, and deleting on an unapproved schedule is the one mistake a later policy cannot repair.  
**Decision:** **Nothing is deleted automatically.** Automated retention enforcement ships **disabled by default** ([RETENTION_AUTOMATED_DELETION_ENABLED](../.env.example)): user data, audit records, and operational records are kept until the deployment's operator approves a policy and turns enforcement on, at which point only the approved windows apply. **Account deactivation and data deletion are separate operations**, and **no administrator-facing account-deletion feature exists** — an administrator deactivates, reactivates, bans, or unbans, and can never destroy a user's records ([AUTH-34](PRODUCT_REQUIREMENTS.md#account-states), `PRIV-33`). **Export and deletion workflows are designed for and deliberately not implemented** (`PRIV-33`): the schema, the authorization boundary, and the interfaces reserve the place where they will go, so adding them is a feature, not a rewrite. The current temporary policy — what exists, where it lives, what backups mean for a future deletion, and what is still unresolved — is written down in [data classification](security/data-classification.md) §4. **Before a production deployment, the operator defines and approves the retention, deletion, export, and audit-log policies** ([PRIV-34](security/data-classification.md#5-privacy-defaults)), and the product makes no statement that a retention period or an indefinite retention is universally acceptable, and no claim of legal compliance.  
**Alternatives considered:** Enforce the documented windows now (rejected: irreversible, unapproved, and different in every deployment); build export and deletion now (rejected: the obligations that shape them are exactly what is not yet known, so the implementation would be reworked); delete only audit records on a schedule (rejected: audit evidence is the record a dispute needs, and it is the last data class that should be discarded before a policy exists); keep an administrator "delete user" action for tidiness (rejected by the owner: the two operations stay separate, and an irreversible admin action in a system with no approved policy is a hazard, not a feature).  
**Consequences:** Development and test data accumulate — accepted deliberately, and the disk-growth runbook ([operations](operations/README.md)) names the remedy; the retention table in [data classification](security/data-classification.md) §4 is **candidate policy**, enforced only when enabled; the privacy notice ([PRIV-31](security/data-classification.md#5-privacy-defaults)) states the deployment's configured values and never a universal one; a future deletion workflow must decide and document what happens in backups, because deleting from the live store does not reach an off-host copy ([OPS-82](operations/README.md)); tests assert the defaults hold (`QA-125`).  
**Revisit when:** A deployment approves its policies and asks for enforcement, or the export and deletion workflows are scheduled — either way as a new decision that names the obligations it implements.

### ADR-027 — Deployment-specific law and data residency; no single jurisdiction
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-26](#open-questions) asked which jurisdiction and legal regime apply to the operator, the users, and the stored location data. The answer is that this product is an **enterprise application installed inside each customer's own network or self-managed infrastructure**, so the deployer is the operator: the jurisdiction, the legal regime, the hosting location, the data-residency duties, and the privacy requirements differ per deployment, and none of them is a property of the software. A pack that assumes one jurisdiction would be wrong for most deployments and would invite compliance claims the project cannot support.  
**Decision:** The project **assumes no jurisdiction, no legal regime, no hosting location, and no universal retention policy**. Those are **deployment configuration and deployment documentation**: the operating organization, the applicable jurisdictions, the data-residency requirements, the privacy requirements, and the retention obligations are recorded per deployment in a **deployment profile** ([OPS-85](operations/README.md)) that also lists which settings must be reviewed for that deployment. During development these legal and operational questions are **marked unresolved** — in the open-question register, in [data classification](security/data-classification.md) §4, and in the deployment profile template — and the pack never asserts that a requirement is met. **Before each production deployment, the customer or responsible operator identifies the applicable legal requirements and approves** the privacy notice, the data-retention rules, the deletion and export procedures, the audit-log policies, and the handling of location data ([PRIV-34](security/data-classification.md#5-privacy-defaults), [PRIV-35](security/data-classification.md#5-privacy-defaults)). Requirements are configurable where the technology allows it; where a duty genuinely needs code, it is implemented behind configuration and documented as deployment-specific, never as a default for everyone. The project makes **no claim of legal compliance** ([GOV-91](development/00-repository-conventions.md#1-language-and-documents)).  
**Alternatives considered:** Pick a default jurisdiction such as the operator's assumed EU/GDPR setting (rejected by the owner: it is not this project's obligation to assume, and the assumption would be wrong where the deployment is elsewhere); enforce a single global retention policy (rejected: it contradicts [ADR-026](#adr-026--retention-and-deletion-are-policies-not-defaults-nothing-is-deleted-automatically-yet) and the deployment model); say nothing until a deployment appears (rejected: the pack must state which decisions and settings are owed, and by whom, or they are discovered during an audit); claim "GDPR-ready" or similar (rejected: an unsupportable claim, and the deployment's law may not be GDPR at all).  
**Consequences:** The privacy notice is a **deployment** document: the pack ships its structure and the rules it must satisfy ([PRIV-31](security/data-classification.md#5-privacy-defaults)), and each operator publishes the version that matches its configuration; the project's own documents describe duties as "the operator's" rather than "ours"; the deployment profile is a review artefact before production ([OPS-85](operations/README.md)); location data handling — the most jurisdictionally sensitive material — is explicitly on the operator's approval list; a future hosted multi-tenant offering would be a different product decision and a new ADR.  
**Revisit when:** The project is offered as a hosted service rather than self-managed software, or a deployment's requirement genuinely cannot be met by configuration and must be implemented in the codebase.

### ADR-028 — Configurable scalability with measured baselines; no capacity claims without measurement
**Status:** Accepted (owner decision, 2026-10-14)  
**Date:** 2026-10-14  **Owner:** Repo owner  
**Context:** [Q-12](#open-questions) asked for the concurrency, event rate, latency SLO, and server budget that load tests should target. Those numbers depend on the deployment: an enterprise installation may run on one modest server or on managed infrastructure, with very different user counts and event rates, and a budget hard-coded for one is wrong for the other. The pack also had no measurable pass/fail criterion at all, so "performance" could be asserted but not tested, and the availability objective ([OPS-83](operations/README.md)) was waiting on the same numbers.  
**Decision:** Scalability is **configuration, not a promise**. The application ships with **no hard-coded resource limits or performance targets** where configuration can carry them; a **baseline load-test profile** for development and CI is documented with explicit, measurable pass/fail criteria ([performance](performance/README.md), `OPS-86`), and **each deployment defines and validates its own production capacity targets** — concurrent users, request rates, event rates, latency SLOs, CPU and memory budgets, and disk limits — from the same fields. Testing includes **load, stress, and recovery** runs; **resource utilization and error rates are monitored**; and **every benchmark documents the hardware and workload assumptions** behind it. **No claim of `unlimited scalability` is made, and production capacity is never stated without measured results** (`GOV-91`). Capacity is adjustable as demand rises or falls, and the **architectural and infrastructure requirements for horizontal and vertical scaling are documented** per deployment (`OPS-87`). Performance work optimizes for predictability and maintainability rather than reaching for numbers the deployment cannot verify.  
**Alternatives considered:** Fixed numeric budgets in the repository (rejected: wrong for most deployments and unverifiable without their hardware); no budgets until production (rejected: CI then cannot fail on a regression, and the pack could not tell a fast release from a slow one); a single benchmark on the development machine presented as capacity (rejected: it measures the machine, not the deployment, and would be quoted as a promise); promising horizontal scaling without documenting its prerequisites (rejected: the shared-state constraint ([ADR-008](#adr-008--single-replica-core-api-until-shared-state-exists)) makes that promise conditional, and a conditional promise stated as unconditional is a future outage).  
**Consequences:** The [performance](performance/README.md) file carries the baseline profile's shape and the measurement rules, and CI compares against the baseline rather than against a number from someone else's server; [OPS-44](ARCHITECTURE.md#6-performance-and-resource-management) budgets become per-deployment values with the shape fixed by the pack; the availability objective ([OPS-83](operations/README.md)) is set against the deployment's approved capacity targets instead of a guessed profile; the single-replica constraint ([ADR-008](#adr-008--single-replica-core-api-until-shared-state-exists)) is named as the first scaling prerequisite, alongside shared state for counters, sessions, and streams; Phase 1's exit gate requires the baseline profile to exist with its pass/fail criteria.  
**Revisit when:** The baseline profile needs different metrics, a deployment's measured results show the architecture cannot meet its targets, or the reuse of a shared component changes the scaling prerequisites.

### ADR-029 — Phase 1 infrastructure is owned minimal implementations behind swappable interfaces
**Status:** Accepted (2026-10-14, Engineering) — **not owner-ratified**: the owner requested an evidence review on 2026-10-15 before deciding ([Phase 1 exit review](development/10-phase-1-exit-review.md) §6), and work that depends on this decision waits for that decision. On 2026-10-16 the owner kept all four decisions pending and the implementations in place provisionally; the migration runner's lock and statement bounds are tracked as the Phase 2 requirements `OPS-90` and `OPS-91`, which bind whichever runner is ratified, the web edge's limitations and the reverse-proxy requirement for real deployments are documented in [operations](operations/README.md#web-edge-limitations-and-the-reverse-proxy-requirement), and client-address propagation through the edge is tracked as the Phase 2 requirement `SEC-75`  
**Date:** 2026-10-14  **Owner:** Engineering  
**Context:** The skeleton needs structured logging with one redaction layer (`SEC-57`, `PRIV-10`), correlation identifiers across hops (`SEC-73`), metrics on a non-public interface (`OPS-63`), liveness/readiness routes (`OPS-59` … `OPS-61`), the error envelope (`API-11`), graceful shutdown (`OPS-62`), a bounded database pool and a reversible migration runner (`OPS-48`, `OPS-20`, `QA-15`), and a production web server for the built bundle (`OPS-01`). Maintained third-party candidates exist for each (pino, prom-client, node-pg-migrate or umzug, nginx or an Express-based proxy), but every candidate either fails a pack rule or adds weight the skeleton does not use: pino's redaction is path-based, while `PRIV-10` requires one deep key-based layer that never depends on callers naming the right paths; prom-client's value starts at histograms and alerting, which arrive in later phases; a migration runner library would still leave the cluster bootstrap (roles, schemas, grants) as owned code; and nginx would add a second runtime family that `QA-123` and `OPS-84` do not cover. The pack's own rules point the same way: lean dependencies (`GOV-13`), the smallest owned implementation over a heavier package (`GOV-80`), and one pinned production runtime (`ADR-025`).  
**Decision:** Phase 1 infrastructure is **owned, minimal, and behind swappable interfaces**: `packages/server-runtime` (logging, redaction, correlation, metrics, health routes, envelope wiring, shutdown — new requirement `OPS-88`), `packages/db` (pool factory, migration runner and CLI, cluster bootstrap — new requirement `OPS-89`), and the dependency-free web static server with a fixed-upstream proxy (`apps/web/server`). Each piece is small, exhaustively unit-tested, and exported through an interface an app consumes, so replacing any of them with a maintained package later is a package-internal change, not an app rewrite. The only new third-party runtime dependencies are `pg` (the PostgreSQL driver — the platform's own client) and, for tests only, `embedded-postgres` (real PostgreSQL 18 binaries, MIT, recorded in the dependency policy).  
**Alternatives considered:** pino with `redact` paths (rejected: path-based redaction is weaker than the single deep layer `PRIV-10` requires, and it ships a dependency tree); prom-client (deferred: adopted when histograms, SLO alerting, or dashboards arrive — the registry interface is the seam); node-pg-migrate or umzug (rejected: the cluster bootstrap and permission conventions remain owned code either way, so the library would sit beside a runner, not replace it); nginx or Caddy for the web edge (rejected: a second runtime family outside `QA-123`, and the same-origin proxy is ~100 owned lines with the SSRF surface closed by construction); Express plus http-proxy-middleware (rejected: two dependencies for behaviour the static server already covers).  
**Consequences:** The redaction layer is single and deep (`PRIV-10`); metric labels are bounded at construction (`OPS-63`); migrations are reversible and checksummed by construction (`QA-15`, `QA-49`); the web edge never resolves a user-controlled upstream (`SEC-48`), and it is not an internet-facing edge — TLS termination, HSTS, and edge timeouts and limits fall to a TLS-terminating reverse proxy in front of it in every real deployment (`SEC-40`, `PRIV-08`); every owned component carries dedicated tests and is smoke-tested as a built artefact (`QA-123`); the maintenance burden is explicit, small, and owned — the phase report records it as residual risk with the replacement seams named. ARCHITECTURE §5 gains `OPS-88`/`OPS-89`, and the identifier count moves to 691.  
**Revisit when:** Observability needs histograms, tracing, or alert routing (evaluate prom-client/OpenTelemetry then); any owned component grows beyond a few hundred lines; a security review finds a maintained package materially safer; or the web edge needs capabilities beyond static serving and one fixed proxy prefix.
